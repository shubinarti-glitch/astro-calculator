# Установка и восстановление Robokassa на astrosmap.ru

Проверено 13 ноября 2026 года на действующем сайте. Инструкция относится к существующему проекту AstroSMap (FastAPI, SQLite, frontend на JavaScript), а не к установке произвольного CMS-модуля.

## 1. Зафиксированное рабочее состояние

- Production: `/opt/astro`, служба `astro`, домен `https://astrosmap.ru/`.
- Идентификатор магазина: `astrosmap`. В кабинете магазин активен.
- Алгоритм в кабинете и конфигурации сайта: `md5`.
- Исправление кода: коммит `2de2da8` в ветке `codex/robokassa-port-release-20261110`.
- Боевые пароли находятся только в `/opt/astro/data/robokassa.json`. Значения в эту инструкцию и Git не включаются.
- Исправленным кодом Robokassa приняла все шесть тарифов с проверенными тестовыми ключами. Затем со вновь введёнными полными боевыми ключами приняла все шесть боевых запросов.
- Пользователь совершил настоящую покупку PDF за 169 ₽ через обычный интерфейс сайта. Robokassa показала операцию как выполненную; подписанный POST callback получил HTTP 200; заказ стал `succeeded`; создано одно событие успешной оплаты. В аккаунте отобразилось подтверждение покупки.
- В карточке операции Robokassa показала «Чек выдан» и ссылку на чек НПД на домене `lknpd.nalog.ru`.
- Прошли 25 тестов Robokassa и платёжной логики, с одним предупреждением Starlette/httpx.

Границы проверки: реальная покупка проверена для PDF за 169 ₽. Реальные списания по остальным пяти тарифам, возврат денег, доставка чека на email и скачивание самого PDF в этой проверке не выполнялись. Общий баланс PDF-кредитов после покупки составлял 4; это общий баланс, а не число кредитов, выданных одним платежом.

## 2. Что именно помогло устранить ошибку 29

Было два независимых препятствия.

1. **Дополнительное кодирование `SuccessUrl2` при расчёте подписи.** На одной и той же проверенной тестовой паре ключей полный запрос с исходным URL в подписи принимался, а с `quote(SuccessUrl2, safe="")` получал код 29. Изменение проверено внешним ответом Robokassa, а не только локальным тестом. `Receipt` при этом оставлен в URL-кодированном виде.
2. **Несоответствие прежней боевой конфигурации рабочим полным ключам.** Даже минимальный запрос без чека, редиректа и `Shp_*` с прежним боевым Паролем №1 отклонялся через GET и POST. После скрытого ввода пользователем полных исходных боевых паролей все шесть боевых запросов были приняты. Точное посимвольное различие старого и нового секрета не устанавливалось; утверждать, какой символ был потерян, нельзя.

Последние два символа прежних серверных ключей совпадали с боевыми полями кабинета. **Это не доказало полного совпадения.** Длина ключа сама по себе также не устанавливает его правильность.

Отдельная ошибка диагностики: проверка `HTTP 200` и слов «оплата/card/payment» в HTML давала ложный успех. Robokassa возвращала HTML-оболочку с заголовком «Безопасная оплата», но внутри уже находилось `RoboxContext.error.code = 29`.

## 3. Подготовка к установке или восстановлению

1. Прочитать `AGENTS.md`, проверить `git status` и состав нужного релиза. Сохранить посторонние незакоммиченные изменения.
2. Проверить, что устанавливается рабочая версия `backend/robokassa.py`, включая исправление `2de2da8`, и что код сайта вызывает именно её.
3. До замены production-кода сохранить резервную копию затрагиваемых файлов. Отдельно сохранить конфигурацию Robokassa с ограниченными правами доступа; она содержит секреты.
4. Проверить HTTPS сайта, доступность backend и проксирование `/api/robokassa/result` без авторизации пользователя. Веб-сервер должен передавать корректные host/scheme приложению: URL возврата строится из `request.base_url`.
5. Получить в кабинете правильный идентификатор магазина, алгоритм и полные технические пароли нужного режима. Пароль входа в личный кабинет — другой секрет. Маски `********…` не являются ключами.
6. Для режима самозанятого проверить подключение фискализации НПД / Робочеков и необходимые полномочия в кабинете. Передача `Receipt` сама по себе не подтверждает, что чек выдан.

Не перезаписывать боевую конфигурацию тестовым шаблоном из локальной копии и не переносить `data/app.db` с рабочего сервера ради проверки.

## 4. Настройки магазина в кабинете Robokassa

Открыть магазин → «Технические настройки».

| Поле | Значение для этого проекта |
|---|---|
| Идентификатор магазина | `astrosmap` |
| Алгоритм расчёта хеша | Совпадает с `hash_algorithm` на сервере; проверенный боевой вариант — MD5 |
| Result URL | `https://astrosmap.ru/api/robokassa/result` |
| Метод Result URL | **POST** |
| Success URL | `https://astrosmap.ru/?payment=check`, метод GET |
| Fail URL | `https://astrosmap.ru/`, метод GET |

При успешной покупке код передаёт индивидуальный `SuccessUrl2` с UUID попытки. Сохранённый в кабинете базовый Success URL не заменяет эту привязку к конкретному заказу. Возврат по Fail URL не выдаёт доступ; незавершённый заказ может оставаться `pending`.

Не путать обычный **ResultURL** с дополнительным **ResultUrl2**: текущая интеграция принимает обычное уведомление формы, а не JWS для дополнительного callback. Сохранить историческую интеграцию YooKassa для старых заказов.

## 5. Серверная конфигурация

Файл: `/opt/astro/data/robokassa.json`. Шаблон ниже содержит обозначения, которые нужно заменить реальными значениями в защищённой конфигурации, а не публиковать:

```json
{
  "merchant_login": "astrosmap",
  "password1": "ПОЛНЫЙ_ТЕХНИЧЕСКИЙ_ПАРОЛЬ_1_НУЖНОГО_РЕЖИМА",
  "password2": "ПОЛНЫЙ_ТЕХНИЧЕСКИЙ_ПАРОЛЬ_2_НУЖНОГО_РЕЖИМА",
  "hash_algorithm": "md5",
  "is_test": true
}
```

- Для тестов использовать тестовую пару и `is_test: true`.
- Для реальной оплаты использовать боевую пару и `is_test: false`.
- `is_test` — JSON boolean, без кавычек. Смена флага без смены соответствующей пары не является настройкой режима.
- Пароль №1 подписывает исходящий запрос; Пароль №2 проверяет входящее подтверждение оплаты.
- Вводить полные исходные значения без пробелов в начале/конце. Не пытаться восстановить ключ по двум видимым символам и не подбирать его.
- Не выводить конфигурацию, подписи, исходную строку с паролем или ключи в терминал, чат, frontend, отчёты и коммиты. Ограничить доступ к конфигурации и резервным копиям (например, `0600`, если владелец файла совпадает с пользователем службы).

Вместе с отдельной копией этой инструкции предоставлен `Repair-RobokassaConfig.ps1`. Он предназначен для **существующего сервера** `/opt/astro` и рабочего кода подписи: скрыто запрашивает боевые пароли, проверяет полный запрос каждого из шести тарифов и лишь при успехе сохраняет конфигурацию с резервной копией. Запускается в PowerShell:

```powershell
& 'ПОЛНЫЙ_ПУТЬ_К_ФАЙЛУ\Repair-RobokassaConfig.ps1'
```

Для этого скрипта нужен существующий SSH-доступ, включая файл `$env:USERPROFILE\.ssh\astro_key`. Он не устанавливает весь сайт с нуля, не меняет пароли в кабинете, не создаёт записи заказов в БД и не оплачивает запросы. Пароль №2 не может считаться проверенным только по открытию формы: его подтверждает настоящий подписанный callback. Скрипт использует конфигурацию с диска; приложение читает её при каждом создании платежа, поэтому для одной замены этого JSON рестарт не требуется. При изменении Python-кода службу нужно перезапустить.

## 6. Как устроен платёж

```text
Кнопка тарифа в авторизованной сессии
  → POST /api/billing/create
  → backend/payments.py: цена и план с сервера
  → backend/robokassa.py: InvId, UUID attempt, Receipt, подпись
  → backend/sales.py: заказ pending и метаданные в одной транзакции
  → переход на auth.robokassa.ru
  → оплата пользователем
  → POST /api/robokassa/result от Robokassa
  → проверка подписи №2, суммы, InvId и Shp_attempt
  → транзакция: succeeded + права покупки + событие
  → возврат браузера и POST /api/billing/check
  → подтверждение на сайте
```

Возврат браузера не подтверждает оплату. Выдача покупки выполняется по проверенному серверному уведомлению. Условное обновление `pending → succeeded` в той же транзакции защищает от повторного начисления при повторном callback.

Основные файлы: `backend/robokassa.py`, `backend/payments.py`, `backend/sales.py`, `backend/main.py`, `frontend/js/app.js`, `frontend/js/sales.js`, `tests/test_robokassa.py`, `tests/test_sales_funnel.py`.

## 7. Правила подписи в проверенной реализации

Текущая строка исходящей подписи:

```text
MerchantLogin:OutSum:InvId:ReceiptEncoded:SuccessUrl2Raw:GET:Password1:Shp_attempt=UUID
```

Здесь `ReceiptEncoded = quote(compact_json_receipt, safe="")`, а `SuccessUrl2Raw` — исходная строка URL с `payment=check&attempt=UUID`. Дополнительный `quote()` для URL **внутри этой подписи** не применять. Затем весь словарь полей кодируется стандартным `urlencode(fields)` для передачи по HTTP. Кодирование транспорта и подготовка значения для хеша — разные этапы. Для других комбинаций дополнительных параметров порядок нужно заново сверять с документацией, а не механически копировать эту формулу.

Входящая подпись строится из исходного строкового значения суммы, InvId, Пароля №2 и отсортированных `Shp_*`. Не менять формат суммы перед хешированием: в реальном callback могут быть шесть десятичных знаков. Отдельно проверить сумму и принадлежность попытки сохранённому заказу. После принятия уведомления ответить `OK{InvId}`.

Чек формируется на сервере из состава тарифа: сумма позиций совпадает с ценой; `payment_method: full_payment`, `payment_object: service`, `tax: none`. Комбинированные тарифы содержат подписку и консультацию отдельными позициями. В текущем НПД-сценарии `sno` не передаётся. Эти настройки нельзя переносить без проверки на другой налоговый режим.

## 8. Проверка перед включением и после релиза

1. Запустить из корня проекта целевые тесты:

   ```powershell
   .\venv\Scripts\python.exe -m pytest tests/test_robokassa.py tests/test_sales_funnel.py -q
   git diff --check
   ```

   В Linux использовать Python из окружения проекта. Сохранять тест, который отклоняет вариант подписи с дополнительно закодированным SuccessUrl2.

2. Проверить все шесть тарифов в тестовом режиме. В HTTP-проверке разобрать JSON-объект `RoboxContext`: успешная инициализация требует отсутствия ошибки, наличия заказа и ожидаемого режима. Это внутренний формат страницы Robokassa, он может измениться; если объект отсутствует или не разбирается, результат **неизвестен**, а не успешен.
3. После развёртывания сверить SHA256 фактически установленного файла, состояние `astro` и HTTP-ответ сайта. Успех локальных тестов не доказывает, что сервер использует этот код.
4. Открыть публичный сайт в авторизованной сессии, выбрать тариф и увидеть настоящую форму Robokassa с нужной суммой. Использовать новую попытку: уже созданные ссылки сами не изменяются после исправления кода или ключа.
5. До настоящего списания получить согласие пользователя. После его оплаты сопоставить конкретный заказ в кабинете провайдера и БД сайта, а не просто выбрать последний успешный заказ вообще.
6. Проверить POST callback с корректной подписью, `succeeded`, однократную выдачу соответствующего права и подтверждение на сайте. Неверная подпись не должна выдавать доступ; повторное корректное уведомление не должно выдавать покупку повторно.
7. Проверить чек в карточке операции: статус «Чек выдан», сумма, наименование услуги и ссылка ФНС / «Мой налог». Доставку на почту проверять отдельно. Для PDF дополнительно скачать отчёт и проверить файл, если требуется приёмка выдачи самого продукта.

Статусы в отчёте всегда различать: «форма открылась», «оплачено», «callback принят», «покупка выдана», «чек выдан», «продукт скачан». Не объявлять всю цепочку проверенной по одному из них.

## 9. Если ошибка 29 повторится

Вести журнал «гипотеза → проверка → результат → следующий шаг». Не менять один и тот же параметр по кругу без новых данных.

| Проверка | Что выясняет |
|---|---|
| Минимальный запрос: MerchantLogin, сумма, уникальный InvId, подпись | Принимает ли провайдер базовую комбинацию магазин / ключ / алгоритм / режим |
| Добавить Shp_attempt | Совпадают ли имя, регистр и значение дополнительного параметра в подписи и запросе |
| Добавить Receipt | Правильны ли состав чека и его кодирование |
| Добавить SuccessUrl2 и метод | На каком этапе появляется расхождение редиректа |
| Сопоставить с запросом через сайт | Отличается ли реальный API-путь, конфигурация процесса, host/scheme или версия кода |

Использовать одну проверенную пару ключей при сравнении вариантов. Если минимальный запрос отклоняется, сначала проверять полные ключи, идентификатор, алгоритм и режим. Если минимальный принимается, а полный нет — изолировать добавляемые поля. Наличие ошибки в одном слое не исключает второй независимый дефект, как произошло 13.11.2026.

После трёх неудачных попыток одной линии диагностики сменить уровень проверки. Не отключать подписи, не помечать заказ оплаченным вручную ради зелёного результата и не генерировать новые ключи без согласования. Внешняя проверка должна читать фактическую ошибку провайдера; HTTP 200, заголовок страницы и общие слова об оплате не являются критериями успеха.

Если callback не приходит, сверить URL и POST в кабинете, HTTPS и проксирование, журнал запросов к точному маршруту. Если он отклоняется — сверить Пароль №2, алгоритм, исходную сумму, InvId и Shp_attempt. Логи диагностировать без вывода секретов и персональных данных.

## 10. Откат

При неуспешном релизе восстановить только затронутые файлы из его резервной копии и перезапустить `astro`; повторить проверку сайта. Конфигурацию восстанавливать из защищённой копии только при совместимости с текущими ключами кабинета. Если ключи в кабинете уже изменились, старый JSON не станет рабочим после отката кода. Не откатывать рабочую БД ради отмены изменения платёжной подписи. Возврат реального платежа — отдельная финансовая операция, требующая согласия пользователя.
