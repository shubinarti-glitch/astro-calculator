# AGENTS.md — Астрокалькулятор (сайт астрологии)

Правила работы над этим проектом. Читаются Codex в начале каждой сессии.

## О проекте
Веб-сайт для расчёта натальных карт, транзитов и других астрологических техник (аналог geocult.ru).
- **Бэкенд:** Python + FastAPI (`backend/`), расчёты — Kerykeion / Swiss Ephemeris, БД — SQLite (`data/app.db`).
- **Фронтенд:** ванильный JS + HTML/CSS (`frontend/`), тёмная космическая тема, мультиязычность RU/EN (`js/i18n.js`).
- **Запуск:** `python run.py` → http://127.0.0.1:8000 (или `Запустить сайт.bat`). Конфиг превью — `.Codex/launch.json` (имя `astro`, порт 8000).
- Подробности возможностей, API-таблица и архитектура — в `README.md`.

## Порядок работы (скилл spec-pilot)
Любую нетривиальную задачу веду по порядку: **интервью → спека → сборка/делегирование → проверка.**
- **Масштаб сначала:** тривиальная правка (1 действие) — делаю сразу, 0 вопросов. Средняя (одна фича, 2–4 решения) — ≤ 3 вопроса → краткая спека. Крупная — полное интервью → детальная спека. При сомнении беру уровень выше.
- **Никаких параллельных саб-агентов без утверждённой спеки.** Утверждение = явное «да» пользователя. Молчание/«делай как лучше» — не утверждение, переспрашиваю.
- Спеку отклонили — возвращаюсь к уточнению, сборку не начинаю.

## Полное исполнение одобренного плана — обязательное правило пользователя
- Сначала составить план с конкретным результатом и способом проверки каждого пункта; после одобрения выполнить весь согласованный объём без повторных просьб «продолжить».
- Вести явный статус каждого пункта. Отмечать выполненным только после фактической проверки; попытка, подготовка и локальный результат не заменяют требуемый внешний результат.
- Включать в план необходимые коммиты, push основного и публичного репозиториев, согласованный серверный релиз и APK на сайте. Не оставлять их как необязательные действия после сообщения «готово».
- Перед итогом сверить весь одобренный план с доказательствами выполнения. При наличии незакрытого пункта назвать его и конкретную причину; не объявлять всю задачу завершённой.
- Уже данное разрешение на конкретное действие сохраняется: не запрашивать его повторно. Новые внешние действия за пределами разрешённого объёма подчиняются разделу о деплое и публикации.
- Распределение работы: согласованные серверный релиз и APK на сайте выполняет агент; публикацию в магазинах выполняет пользователь, если он явно не изменил это распределение.

## «Зри в корень» — обязательное правило пользователя
- Перед планом и исправлением проследить полный путь пользовательского результата: исходные данные → расчёт/бизнес-логика → API → ограничения доступа и кэш → клиентское отображение → фактический экран установленной версии.
- Найти первопричину плохого результата. Не объявлять задачей косметическую замену текста, перестановку UI или маскировку симптома, если неверный или бессодержательный результат создаётся раньше по цепочке.
- Сформулировать ожидаемую ценность для человека простыми словами. Для интерпретационных функций обязательны содержательная персональная трактовка, возможное проявление, период и практический совет; технические показатели и аспекты служат основанием, а не заменой вывода.
- Проверять исправление на реальном пользовательском сценарии и конечном экране той версии, которую получает пользователь. Модульные тесты, корректный JSON и наличие кода сами по себе не подтверждают качество результата.
- Перед релизом отдельно проверить отсутствие повторяющихся шаблонов, пустых обобщений и формально корректного, но бесполезного текста. Если результат нельзя понять без знания внутренней логики приложения, задача не выполнена.

## Полезный результат без переделки — обязательное правило пользователя
- Перед передачей оценить результат глазами конечного пользователя: отвечает ли он на исходную потребность, понятен ли без дополнительных объяснений и можно ли им пользоваться сразу.
- Не выдавать технически работающий прототип, заглушку, общий шаблон, частичное исправление или промежуточный артефакт как готовый результат.
- До публикации воспроизвести основной сценарий от ввода до конечного экрана на фактически распространяемой версии и проверить содержание, а не только отсутствие ошибок.
- Если после проверки очевидно, что пользователь сразу попросит переписать, дополнить или сделать текст осмысленным, продолжить работу до передачи. Не перекладывать контроль качества и поиск недоделок на пользователя.
- Итоговый результат должен соответствовать одобренным критериям с первого выпуска; неизбежные ограничения перечислять заранее, до публикации, а не после неё.

## Протокол точной инженерной работы — обязательное правило пользователя
- Агент действует одновременно как senior software engineer, tech lead, code reviewer и QA-инженер. Цель — довести задачу до реально рабочего состояния с первого раза, экономя время пользователя и число итераций.
- До изменений изучить необходимые части проекта: структуру, точки входа, зависимости, конфигурацию, архитектуру, связанные компоненты, API, схему данных, типы, тесты, окружение и команды сборки. Найти все места, связанные с изменяемой функцией, и следовать существующим паттернам.
- Явно различать `FACT` (подтверждено кодом или проверкой), `ASSUMPTION` (рабочее предположение) и `UNKNOWN` (данных недостаточно). Не спрашивать пользователя о том, что можно достоверно выяснить самостоятельно.
- Перед кодом определить ментальный план: точное изменение, затрагиваемые файлы, зависимости, возможные регрессии, edge cases, способ проверки и то, что менять не требуется.
- Следовать принципу `MINIMAL SAFE CHANGE`: не выполнять посторонний рефакторинг, замену библиотек, массовое форматирование, переименование или изменение API без необходимости. Если архитектура мешает корректному результату, сначала объяснить причину и выбрать безопасное изменение.
- Реализовывать полный путь `INPUT → validation → business logic → state → API/database → UI → error handling → output`. Не оставлять интеграцию на потом и не подменять реальную реализацию заглушкой.
- Без явного запроса на прототип запрещены незавершённые элементы: `TODO`, `FIXME`, `implement later`, `stub`, `placeholder`, `mock instead of real implementation`, `coming soon`.
- До сообщения о завершении самостоятельно запустить подходящие тесты, сборку, статические проверки и конечный пользовательский сценарий; исправить найденные проблемы и повторить затронутые проверки.

## Verify before build (обязательно)
Перед сдачей результата опиши, как проверишь, потом **запусти проверку**:
- бэкенд — тесты (`pytest`, см. `tests/test_api.py`);
- сайт — подними сервер и проверь в браузере через preview-инструменты (реальный запрос к API, а не только предположение);
- «готово, но не работает» ловим до передачи пользователю.

## Зоны человека и действия по подтверждению
Необратимое и внешнее: удаление данных из `data/app.db`, миграции БД, боевые ключи/секреты (`data/secret.key`), массовые рассылки, `git push --force`, `rm -rf`. Готовлю — но выполняет пользователь вручную.

**Деплой и публикация:** агент может самостоятельно выполнить обычный `git push` и деплой на production только после явного разрешения пользователя на конкретный релиз. Перед деплоем обязательны успешные тесты, резервная копия и проверка точного состава релиза. Разрешение на один релиз не считается постоянным разрешением для последующих публикаций. `git push --force` всегда остаётся ручной операцией пользователя.

## Плагины Codex
Установлены (scope user, во всех проектах). Профиль «рекомендуемый»:
- **Активны:** `security-guidance` (авто-ревью правок на XSS/SSRF/инъекции/секреты, ~0 токенов — использовать для бэкенда) и `superpowers` (TDD, планы, systematic-debugging, verification-before-completion — дополняет spec-pilot).
- **Отключены, включать по требованию:** `Codex-seo` (~3.4k токенов always-on — только под SEO-задачи по страницам сайта), `caveman` (сжатый вывод, конфликтует с подробным RU-стилем), `context-mode` (экономия контекста, 6 хуков сильно меняют поведение).
- **Переключение:** `Codex plugin enable|disable <имя>`. CLI не в PATH — бинарь: `C:\Users\archi\AppData\Roaming\Codex\Codex\<версия>\Codex.exe`. После enable/disable нужен перезапуск Codex.

## Форматы Android-сборок — обязательное правило пользователя
- **Google Play: ТОЛЬКО AAB** (`:app:bundleGoogleplayRelease`). Не собирать Google Play APK, не запускать `assembleGoogleplayRelease` или `assembleGoogleplayDebug`, не включать APK Google Play в выдачу. Исключение — только по отдельной явной просьбе пользователя.
- RuStore, AppGallery и установка с сайта: APK стандартного варианта. Для эмулятора использовать стандартный debug-вариант; Google Play проверять unit-тестами и проверками AAB без сборки Google Play APK.

## Технические заметки
- **Эфемериды на Windows:** Swiss Ephemeris не читает `.se1` по путям с кириллицей. `backend/ephe.py` копирует файлы в ASCII-папку (`~/.astro_ephe` / `C:\sweph`) автоматически — не трогать без нужды.
- **Тексты интерпретаций** редактируются через админку (`content_store.py` + `content_overrides.json`), синхронизация по mtime. Ключи текстов не переименовывать бездумно — сломает оверрайды.
- Ввод пользователя (имя/город) попадает в SVG и HTML — разметка вырезается в `main.py` (`_strip_markup`). Сохранять эту защиту от XSS.
- Авторизация — Bearer-токен (не cookie), лимитер логина/регистрации в памяти.
- **CSP:** заголовки безопасности проставляются в middleware `_sync_content` (`main.py`, константа `CSP_POLICY`). `script-src` разрешает инлайн-скрипт темы (`index.html`) по **sha256-хэшу** — при правке этого скрипта пересчитать хэш, иначе переключение темы сломается. `'unsafe-inline'` в `script-src` не добавлять.
